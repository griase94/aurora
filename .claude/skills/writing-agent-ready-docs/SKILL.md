# Writing agent-ready docs

Coding agents read Aurora through text files, not through the Storybook SPA (an empty shell
without JavaScript). Every agent artifact is **generated by `kit-gen`** from source: the
component, its JSDoc, its `parameters.kit`, its stories and `packages/*/package.json`.
Nobody hand-edits a generated file; fix the source or the generator.

## Hard rules

- **Derive every package fact at build time.** Package names, scope, version, entries and
  repository URL come from `packages/*/package.json` (`name`, `version`, `exports`,
  `repository`). Never type them into prose, UI strings, MDX or generator code: a scope or
  account rename must be a one-line change in `package.json`.
- **API-dense, not narrative.** Per component: facts, examples, rules. No repository tour, no
  history, no maintainer notes (context-file research found overviews do not help agents;
  specific instructions do).
- **Aurora's rules only.** The rules block states what holds for every consumer of Aurora.
  An app's own conventions (its copy language, money format, server folders) belong in that
  app's `AGENTS.md`, never in Aurora's index.
- **The public build (`KIT_PUBLIC=1`) publishes public facts only:** no product-layer or
  undocumented components, no app paths, no internal decision codes, no "which app uses it".
- **Every link resolves in the composed site** (Atlas at `/`, Handbook at `/handbook/`);
  `check-site.ts` proves it.

## The files and their shape

| File | Served at | Contents |
|---|---|---|
| `llms.txt` | `/llms.txt` and `/handbook/llms.txt` | llmstxt.org index: `# Aurora`, a `>` summary, an install-and-set-up section, the rules, then `## <Group>` lists of `- [Name](/handbook/c/<slug>.md): purpose (status) \`import\` [docs](…)` |
| `c/<slug>.md` | `/handbook/c/<slug>.md` | one component, plain Markdown, the fields below |
| `kit.json` | `/handbook/kit.json` | the same facts as JSON, plus tokens |
| `llms-full.txt` | `/handbook/llms-full.txt` | every page's prose, with its address; split into per-section files once it outgrows one agent read |
| `AGENTS.md` | in the npm package and linked from `llms.txt` | how to install, import and theme Aurora |

- In `llms.txt` the component name links to its `.md` page; the Storybook URL comes second.
  An H2 named `Optional` marks links an agent may skip.
- Both site heads declare the text version: `<link rel="alternate" type="text/markdown" href="…llms.txt">`.

## What every component entry carries

1. Name, one-sentence purpose, status (`Stable`, `Beta`, `Deprecated`; a deprecated entry
   names its replacement).
2. Install command and import line, both built from `package.json` and the consumer entry
   (`import { Button } from "<alias>/button"`), never a relative or app-internal path.
3. Props: name, type, required, default (resolved to its value: `"fit"`, not
   `IBAN_REST_FIT`), description from the prop's JSDoc, allowed values generated from the
   variant table, never hand-listed. A compound component lists each part's props.
4. Snippets and events, separate from props.
5. Examples: the code of the specimen stories, as fenced `svelte` blocks, runnable as shown.
6. When to use, when not, and what to use instead (`situation → Component`).
7. Do and don't, each with its reason.
8. Accessibility contract: role, keyboard map, focus behaviour, known gaps.
9. Tokens by semantic name (`--primary`), never raw values.
10. Links: the Handbook page and the Atlas specimen.

`kit.json` carries `schemaVersion` and a `package` block (`name`, `version`, `entries`,
`cssEntry`, theme and brand attributes) so an agent knows which release the facts describe.
Name its component fields like Storybook's component manifest (`id`, `name`, `description`,
`import`, `props`, `stories`/examples): Svelte gets a Storybook manifest only in Storybook 11,
and a matching shape makes the switch cheap.

## Choices already made

- No `Accept: text/markdown` content negotiation: unverified on static hosting. Explicit
  `.md` URLs plus the `alternate` link are the baseline.
- No Storybook MCP docs toolset on Storybook 10: it needs a components manifest, which
  Svelte frameworks do not generate before 11. `@storybook/addon-mcp` may run in local
  `kit:dev` for agents on the dev server; the public contract is the files above.
- `llms.txt` is cheap and helps coding agents on developer docs; it does not move search
  traffic. Judge it by `.md` requests in logs, not by assumption.

## Verify

```sh
KIT_PUBLIC=1 KIT_SITE_URL=/handbook pnpm -C apps/docs kit:gen
ls apps/docs/src/lib/kit/generated/public                   # llms.txt, llms-full.txt, kit.json, c/
# No hard-coded package name outside package.json (prints nothing):
for p in packages/*/package.json; do n=$(node -p "require('./$p').name"); git grep -nF "$n" -- apps/docs/src apps/docs/scripts '*.mdx'; done
# No app-internal import in the public index (prints nothing):
grep -nE '\$lib/|\.\./' apps/docs/src/lib/kit/generated/public/llms.txt
pnpm -C apps/docs site:atlas                                # runs check-site.ts over the composed output
```

Then the agent test: give a fresh agent only `/llms.txt` and the task "add a Stable Aurora
component for a destructive confirm to a new SvelteKit page". It must install the right
packages, import from the public entry, pass only declared props and pick the right
component without opening the Storybook UI. A miss is a missing fact: fix the generator.

## Before you call it done

- Package facts read from `package.json`; nothing typed by hand.
- Each entry has install, import, typed props with real defaults, examples, do/don't.
- The public index holds Aurora's rules and Aurora's components only, and every link resolves.
